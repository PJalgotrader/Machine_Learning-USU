1. What is uv?

uv is a fast Python package and environment manager. It does the jobs you used Conda + pip + virtualenv for, in one tool, and it also downloads Python itself.

The mental model, translated from Conda:

Conda ideauv equivalentWhat it is
A named environment (conda activate myproj)A .venv/ folder inside the projectThe actual installed packages. Lives next to your code, not in a central list.
environment.ymlpyproject.tomlThe list of packages you asked for. Short, human-written.
(no standard equivalent)uv.lockThe exact version of every package that got installed, including the ones you never typed. Machine-written.
conda install python=3.12.python-versionOne line saying which Python this project uses.
Main idea: a uv project is a folder with a pyproject.toml, a uv.lock, and a .venv that uv builds from them. You almost never "activate" anything; you run uv run ... and uv uses the right environment automatically.

2. Install uv (and update it later)

Windows

Open PowerShell and run:

powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

Then close and reopen PowerShell. (Alternative: winget install astral-sh.uv)

macOS / Linux

Open Terminal and run:

curl -LsSf https://astral.sh/uv/install.sh | sh

Then close and reopen Terminal. (Alternative on macOS: brew install uv)

Check that it worked

uv --version

Update uv itself

uv releases often. If you installed it with the commands above:

uv self update

If you installed it with winget or Homebrew instead, update it the same way you installed it: winget upgrade astral-sh.uv or brew upgrade uv. uv will tell you if self update is not the right tool.

Updating uv does not change any of your projects. Package versions are decided by uv.lock, not by the uv version.

3. The three files, explained

pyproject.toml — "what I want"

A short text file you can read and edit. It names the project, says which Python versions it supports, and lists the packages you asked for. This is a course repository's real one, trimmed: 

[project]
name = "course-environment"
version = "2026.9"
requires-python = ">=3.13,<3.14"      # which Python this project needs
dependencies = [
    "pycaret-core==3.5.0",           # exactly this version
    "statsmodels>=0.14,<0.15",       # any 0.14.x
    "lightgbm>=4.0",                 # 4.0 or newer
    "jupyterlab>=4",
]

You do not usually edit this by hand. uv add pandas writes the line for you and uv remove pandas deletes it. The version rules (==, >=, <) are the same ones pip uses.

uv.lock — "what I actually got"

When uv installs your dependencies, each one pulls in its own dependencies, and those pull in more. A request for 7 packages can install 165. uv.lock records the exact version of every one of them, for every operating system, so that a classmate running uv sync next month gets byte-for-byte the same environment you have today.

  • It is generated by uv. Never edit it by hand.
  • It is long and looks scary. You never need to read it.
  • Commit it to Git. That is the whole point: the lock file is what makes the project reproducible.
  • Conda has nothing like it by default, which is why "it works on my machine" happens more with Conda.

.python-version — "which Python"

One line, for example 3.13. uv reads it and uses (or downloads) that Python for the project. Change it with uv python pin 3.14, not with a text editor, so uv can check it is valid.

And .venv/ — the built environment

The folder with the installed packages. It is disposable: delete it any time and uv sync rebuilds it from the two files above in seconds. 

my-project/
├── .venv/              ← built by uv, do NOT commit
├── .python-version     ← commit
├── pyproject.toml      ← commit
├── uv.lock             ← commit
└── main.py

4. The two situations you will be in

A. Someone gives you a project (this course)

The project already has pyproject.toml and uv.lock. You do not create anything, you rebuild it:

git clone https://github.com/PJalgotrader/<course-repo>.git
cd <course-repo>
uv sync
uv run jupyter lab

<course-repo> is Machine_Learning-USU, Deep_Learning-USU or Deep_forecasting-USU. All three work the same way. First uv sync also downloads Python 3.13 if you do not have it. Later ones take seconds.

B. You start your own project

You create the files, then add packages one by one:

mkdir my-project
cd my-project
uv init --python 3.13
uv add numpy pandas scikit-learn matplotlib
uv add --dev jupyterlab ipykernel
uv run python

uv init creates pyproject.toml, .python-version, a .gitignore, a README.md and a starter src/ folder. Only the first two matter to you.

Never run uv init inside a project that already has a pyproject.toml. If the files are there, the only command you need is uv sync.

6. Everyday commands

uv add pandas                # add a package (writes pyproject.toml + uv.lock, installs it)
uv add "pandas>=2.2"         # add with a version rule
uv add --dev pytest ruff     # tools you need while developing, not to run the code
uv remove pandas             # the opposite of add
uv sync                      # make .venv match pyproject.toml + uv.lock
uv run python script.py      # run anything inside the project's environment
uv run jupyter lab           # same idea, for Jupyter
uv tree                      # show the dependency tree
Prefer uv add package-name over pip install package-name. uv add records the package in the project files so everyone else gets it too. pip install changes only your machine and nobody else will know.

If you really want a classic activated shell, it still works: .venv\Scripts\activate on Windows, source .venv/bin/activate on macOS/Linux. Then plain python and jupyter point at the project. Most people stop needing this once uv run becomes a habit.

7. Updating packages and Python

Because of uv.lock, nothing updates by itself. uv sync always installs the locked versions. To move forward you change the lock on purpose, then sync.

You want to…Run
Update one package to its newest allowed versionuv lock --upgrade-package pandas
uv sync
Update every packageuv lock --upgrade
uv sync
Change the rule for a package (for example allow pandas 3)uv add "pandas>=3"
Move the project to a newer Pythonuv python pin 3.14
uv sync
Get a classmate's changes after git pulluv sync
Update uv itselfuv self update
Careful in a shared project. uv lock --upgrade rewrites uv.lock. In this course, that file is maintained by the instructor. Run upgrades in your own projects, not in the course repository, or you will drift away from what the notebooks were tested on.

8. Managing Python versions

uv downloads Python for you. No python.org installer, no Anaconda needed.

uv python list                # what is installed, what is available
uv python install 3.13        # download a version (once, shared by all projects)
uv python pin 3.13            # write .python-version for THIS project
uv run python --version       # confirm which one the project uses

Different projects can use different Pythons. The downloaded versions live in one shared place; each project just points at one of them.

9. Jupyter, VS Code and Cursor

Add Jupyter support to a project (already done in the course project):

uv add --dev jupyterlab ipykernel

Run Jupyter:

uv run jupyter lab

VS Code / Cursor, notebooks inside the project folder

Open the project folder as your workspace. In a notebook click Select Kernel → Python Environments and pick the interpreter inside your-project/.venv. VS Code usually finds it on its own.

VS Code / Cursor, notebooks somewhere else (this course)

The course's .venv sits at the top of the repository while the notebooks live in the Module folders. Register the environment once as a named kernel, and it shows up in every notebook, wherever it is: 

cd <course-repo>

10. What about 10 projects = 10 virtual environments?

Yes. If you have 10 separate projects, you normally have 10 separate .venv folders. This is intentional because each project is isolated.

It is not as wasteful as it looks. uv keeps a global package cache and links files from it instead of downloading and copying everything again for every project. Ten projects that all use pandas share one downloaded copy. 

uv cache dir      # where the cache lives
uv cache prune    # remove entries no project uses any more (safe)
uv cache clean    # delete the whole cache (safe, next sync re-downloads)
Why isolation is good: upgrading NumPy, PyTorch, or pandas for Project B will not accidentally break Project A.

11. When something breaks

SymptomWhat it meansFix
ModuleNotFoundError: No module named 'pycaret' but you installed it You ran a different Python (the system one, or Conda's base), not the project's Use uv run python ..., or pick the .venv kernel in VS Code
Environment feels broken or confusing Something got installed by hand, or half-finished Delete .venv, then uv sync. Nothing is lost: the recipe is in the two files
Still broken after that Cached package is corrupt uv sync --reinstall
Windows: Failed to persist temporary file ... os error 3 Folder path too long (Windows 260-character limit) Move the project to a short path such as C:\dev\my-project
Project lives in OneDrive / Google Drive and everything is slow The sync client is uploading thousands of .venv files Keep projects outside synced folders, or exclude .venv from sync
uv add says versions conflict Two packages cannot agree on a shared dependency Read the last lines of the message, they name the two packages. Loosen one rule, or leave that package out

Delete the environment

Windows PowerShell:

Remove-Item -Recurse -Force .venv

macOS / Linux:

rm -rf .venv

Deleting .venv does not delete your project or dependency list.

The escape hatch

uv pip install something installs into the project's .venv the pip way, without touching pyproject.toml or uv.lock. Useful for a quick experiment. Not recorded, so the next uv sync may remove it, and classmates will not get it. For anything you want to keep, use uv add.

12. A course repository, start to finish

Same steps in all three course repositories. Kernel names are in section 9.

# ten-second test (optional, once per computer)
cd <course-repo>/"Platforms and tools/uv/simple_test"
uv sync
uv run python main.py         # prints your Python version, your pandas version, "uv is working!"

# once
cd <course-repo>
uv sync
uv run python -m ipykernel install --user --name <kernel-name> --display-name "<display name>"

# every time
uv run jupyter lab            # or open a notebook in VS Code and pick the display name

# check
uv run python scripts/check_environment.py   # ends with "Your course environment is ready."

Do not run uv add, uv remove, or uv lock --upgrade in the course repository unless the instructor asks. The lock file is what makes your leaderboard match the one in the lecture.

14. Simple rules

  1. One real project → one .venv.
  2. Got a project with a uv.lock? Run uv sync, nothing else.
  3. Use uv add instead of pip install.
  4. Use uv run instead of relying on environment activation.
  5. Commit pyproject.toml, uv.lock and .python-version.
  6. Do not commit .venv. Never edit uv.lock by hand.
  7. Use --dev for Jupyter, testing, and development tools.
  8. Updates are deliberate: uv lock --upgrade... then uv sync.
  9. If the environment gets messy, delete .venv and run uv sync.
  10. Keep Conda only when you truly need unusual non-Python/system packages.
